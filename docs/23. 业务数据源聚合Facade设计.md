# 23. 业务数据源聚合 Facade 设计（BE-ARCH-06）

> 关联文档：`docs/14. 分布式数据源服务架构.md`（通用框架）、`backend/services/datasource/`（现有实现）
> 状态：v0.2（2026-08-09 复审）— Facade 层已落地（BE-ARCH-06a~f），红线收口已执行（BE-ARCH-07a~o）。
> **§八 为现状 SSOT**（2026-08-09 晚三条标准复审结论）；§一~§五 为设计意图，与 §八 冲突时以 §八 为准。
> 决策结论：新增**业务聚合 Facade 层**，位于 `DataSourceInterface` 薄适配器之上，承接"策略逻辑 + 业务级检测 + 多源融合"，Tools / 业务逻辑只调 Facade，不直接碰底层适配器或外部 API。

## 一、问题背景：当前架构已经是什么样

用户诉求原文：

> 每个数据源，在主服务都有个适配器，适配器链接 http api 以及可能额外的各种策略逻辑和检测逻辑；然后适配器统一向上提供数据源服务，提供业务逻辑和 tools 使用。

经过对 `backend/services/datasource/` 的代码审查，**"适配器 + 统一服务面"已经存在，但被拆成了两个物理层，且"策略逻辑"这一环当前是空缺的**：

### 层 1：`DataSourceInterface` 薄适配器（`services/datasource/adapters/*.py`）

把各具体服务（`FutuService`、`FREDService`、`LegacyYFinanceService` ...）适配为统一接口 `fetch(action, params) -> Result`。

- `name` / `version` / `capabilities`：身份与能力声明。
- `is_available()` / `health()`：连通性与熔断探测（如 `futu.py` 以 OpenD `CONNECTED` 状态为准；`macro.py` 以 API Key 为准）。
- `fetch()`：限流识别（`429/限流/Too Many` → `RATE_LIMITED`）、重试标记、子能力失败隔离（期权链失败不误伤整源）。
- `mode`：经 `DATASOURCE_*_MODE` 控制 `internal/external/hybrid`。
- **关键约束**：现有适配器被文档与注释反复强调是**"薄适配、组合而非改造、不写策略逻辑"**（`futu.py:9`、`macro.py:8`）。它们只做"链接 HTTP API + 基础检测"，**不承接任何业务策略**。

### 层 2：统一服务面（`DataSourceRegistry` + `DataSourceRouter`）

- `DataSourceRegistry`（`source_registry.py`）：持有所有薄适配器实例，主路径 `fetch(source, action, params)` 串起 **限流检查 → 熔断器 → 调用 → 指标上报**（`DATASOURCE_LATENCY/ERRORS/AVAILABILITY`）。这是"向上统一提供数据源服务"的入口。
- `DataSourceRouter`（`router.py`）：external 模式下的 HTTP 代理 / 降级层，负责把请求路由到远程 VPS 节点（带 HMAC 签名）、failover（如 YFinance 主节点限流时切备用节点）。

### 缺口

| 诉求 | 现状 |
|:---|:---|
| 适配器链接 HTTP API | ✅ 已具备（薄适配器 + Router） |
| 适配器做检测逻辑 | ✅ 已具备（health / 限流识别 / 熔断） |
| 适配器放**策略逻辑** | ❌ **空缺**：策略、融合、归一化散落在 router 投票、COMM-01 链接测试、API 路由、agents/Tools 各自拼装 |
| 向上统一提供**业务语义**服务 | ❌ 不完整：Registry 暴露的是底层 `action`（QUOTE/HISTORY...），Tools 仍需自己拼多源、做归一化 |

结论：需要一个**业务聚合 Facade**，把"策略逻辑 + 业务级检测 + 多源融合 + 归一化"收口到统一业务语义接口之后，Tools 只调业务语义，不再直接调 `DataSourceInterface` 的 `fetch`。

## 二、目标架构

```
┌─────────────────────────────────────────────────────────────┐
│  Tools / 业务逻辑 (get_broker_market_data, get_fundamental)  │
│  （只调业务语义接口，不知道底层有几个源、谁在线）              │
└───────────────────────────┬─────────────────────────────────┘
                            │ 业务语义调用 (get_quote, get_history, ...)
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  【新增】DataService Facade  (业务聚合 Facade)                │
│  ───────────────────────────────────────────────────────    │
│  · 业务语义接口 (按领域：行情/基本面/宏观/期权)               │
│  · 策略逻辑：源选择权重、多源融合、报价一致性校验            │
│  · 业务级检测：Stale 检测、字段完整性、跨源偏差告警          │
│  · 归一化：统一 OHLCV / 币种 / 时间粒度 / 命名                │
│  · 业务缓存 + 命中率统计                                     │
└───────────────────────────┬─────────────────────────────────┘
                            │ 统一的 action 语义 (QUOTE/HISTORY/...)
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  DataSourceRegistry + DataSourceRouter（已有，统一服务面）    │
│  限流检查 → 熔断器 → 远程 HTTP(HMAC) → 降级/failover          │
└───────────────────────────┬─────────────────────────────────┘
                            │ fetch(action, params)
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  DataSourceInterface 薄适配器（已有）                        │
│  只管链接底层 + 基础检测，不写策略                           │
└───────────────────────────┬─────────────────────────────────┘
                            │
              ┌─────────────┼──────────────┬──────────────┐
              ▼             ▼              ▼              ▼
        data_subservice  Futu OpenD    FRED API     AKShare 节点
        (远程 VPS)       (主节点)      (远程)        (CN 节点)
```

### 三层职责边界（红线）

| 层 | 允许 | 禁止 |
|:---|:---|:---|
| 薄适配器 (`adapters/*.py`) | 链接底层、基础检测（health/限流/熔断）、协议对齐、结果转换 | 写任何业务策略、多源融合、归一化 |
| 统一服务面 (`Registry`/`Router`) | 限流、熔断、HTTP 路由、failover、指标上报 | 写业务语义、字段语义转换 |
| **业务聚合 Facade（新增）** | 业务语义接口、源选择策略、多源融合、业务级检测、归一化、业务缓存 | 直接 `import` 具体数据源库（yfinance/futu/akshare）、直接发 HTTP 到外部 |

**铁律**：Facade 只能通过 `DataSourceRegistry.fetch(source, action, params)` 取数，禁止 `from backend.services.futu import futu_service` 这类直连，也禁止直接 `httpx.get(yahoo)`。所有底层出口必须走已有薄适配器 + Router（满足 `docs/14 §10.3` 双模运行与单一出口约束）。

## 三、Facade 接口设计

放置位置建议：`backend/services/datasource/business/`（`facade.py` + 按领域拆 `market.py` / `fundamental.py` / `macro.py` / `option.py`）。

### 3.1 核心门面（`facade.py`）

```python
from typing import Any, Optional
from backend.services.datasource import Result
from backend.services.datasource.source_registry import datasource_registry


class DataServiceFacade:
    """业务聚合 Facade：向上提供业务语义，向下经 Registry 取数。

    不直接持有任何具体数据源实例，只通过 datasource_registry.fetch 取数。
    """

    # ---- 业务语义接口（领域方法）----
    async def get_quote(self, ticker: str, prefer_sources: Optional[list[str]] = None) -> Result:
        """行情快照：策略选源 → 多源融合 → 一致性检测 → 归一化。"""
        ...

    async def get_history(self, ticker: str, ktype: str = "K_DAY", num: int = 60,
                          prefer_sources: Optional[list[str]] = None) -> Result:
        """历史 K 线：选源 → 取数 → OHLCV 归一化（时间粒度/复权/币种）。"""
        ...

    async def get_fund_flow(self, ticker: str, prefer_sources: Optional[list[str]] = None) -> Result:
        ...

    async def get_option_chain(self, ticker: str, expiration_date: str = "",
                               prefer_sources: Optional[list[str]] = None) -> Result:
        ...

    async def get_fundamental(self, ticker: str, prefer_sources: Optional[list[str]] = None) -> Result:
        ...

    async def get_macro_series(self, series_id: str, limit: int = 100,
                               prefer_sources: Optional[list[str]] = None) -> Result:
        ...

    # ---- 内部策略原语（可被业务方法复用）----
    async def _select_source(self, action: str, candidate_sources: list[str]) -> Optional[str]:
        """源选择策略：基于 Registry 健康度 + RateLimitRegistry 退避 + 业务权重。"""
        ...

    async def _merge(self, action: str, results: list[Result]) -> Result:
        """多源融合：成功源按权重/新鲜度聚合；全部失败则回退首个错误。"""
        ...

    def _detect_stale(self, data: Any, action: str) -> Optional[str]:
        """业务级检测：数据新鲜度(延迟超过阈值)、字段完整性、跨源偏差。"""
        ...

    def _normalize(self, data: Any, action: str) -> Any:
        """归一化：统一 OHLCV 字段名、时间粒度、币种、复权标记。"""
        ...


data_service = DataServiceFacade()
```

### 3.2 源选择策略（`_select_source`）

优先级（可配置权重，默认）：

1. **健康度过滤**：`datasource_registry.get(name, action)` 已过滤 `is_available()` 为假、且 `capabilities` 不支持该 `action` 的源。
2. **限流退避过滤**：`rate_limit_registry.get_throttler(name).should_throttle()` 为真的源直接跳过（与 `source_registry.fetch` 同源逻辑，Facade 提前预判避免无效调用）。
3. **业务权重**：`DATASOURCE_<NAME>_BUSINESS_WEIGHT`（env，默认 futu=100, yfinance=80, akshare=60, fred=90），高分优先；`prefer_sources` 参数可临时覆盖。
4. **节点位置偏好**：港股/A股偏好 akshare/cn 节点；美股/期权偏好 futu/yfinance；宏观偏好 fred。

### 3.3 多源融合（`_merge`）

- 单源成功 → 直接采用（仍过 `_detect_stale` + `_normalize`）。
- 多源成功 → 按权重与新鲜度加权融合（如报价取新鲜度高且偏差 < ε 的源；超出偏差阈值则触发告警并选新鲜度最高者）。
- 全部失败 → 回退返回首个非限流错误（保留 `source` 字段便于溯源）。

### 3.4 业务级检测（`_detect_stale`）

- **新鲜度**：`Result.latency_ms` + 数据自带时间戳，超过 `STALE_THRESHOLD_MS`（默认按 action 不同：QUOTE 30s、HISTORY 1h）判 stale。
- **字段完整性**：关键字段缺失（如 OHLCV 任一为空）判不完整。
- **跨源偏差**：多源报价差 > `QUOTE_DEVIATION_PCT`（默认 0.5%）判偏差，记录告警指标 `DATASOURCE_QUOTE_DEVIATION`。

### 3.5 归一化（`_normalize`）

统一输出契约（供 Tools 与前端直接使用）：

- OHLCV 字段名：`open/high/low/close/volume`（统一小写下划线），时间字段 `time`（ISO8601 / Unix 秒双支持）。
- 币种标注：港股 `HKD`、美股 `USD`，缺失则按 ticker 后缀推断并标注 `currency`。
- 复权标记：`adjust` ∈ `{none, qfq, hfq}`，默认 `qfq`。

## 四、与现有调用方的对接

### 4.1 Tools 接入

现有 Hermes Tools（如 `get_broker_market_data`）当前若直接走 `legacy_market_data` 路由或 `DataSourceRegistry`，改为统一调 `data_service.get_quote(...)` 等业务方法。**Tools 不再感知"有几个源、哪个在线"**，只拿业务语义结果。

### 4.2 薄适配器无需改动

薄适配器维持"薄"的契约不变；Facade 只通过 `datasource_registry.fetch` 调用它们，符合 `docs/14 §10.2` Registry 访问原则（主 app 只经 `DataSourceRegistry`）。

### 4.3 降级路径保留

Facade 内部融合失败时，最终仍回退到 `DataSourceRegistry.fetch` 的既有降级/熔断逻辑，不破坏 `docs/14` 已有的可用性保障。

## 七、BE-ARCH-06f 落地：宏观日历统一经 Facade 聚合（2026-08-07）

### 问题
`fred` / `dbnomics` / `rbi` 三源虽已注册进 `DataSourceRegistry`（经 `ensure_macro_sources_registered`），且都在 `capabilities` 声明了 `ECONOMIC_CALENDAR`，但 Router 的 `economic_calendar` action **只派给 akshare**，三源实际仅经 `routers/datasource_vote.py` 直连投票，绕过了 Facade 的权重 / 融合 / 降级逻辑。属于"注册了但没被业务聚合层收口"的缺口。

### 设计决策
- **互补而非替代**：akshare 给传统财经事件日历（非农 / FOMC / 财报），fred/dbnomics/rbi 给 **CPI actual 回填**（fred 前瞻带 estimate，dbnomics/rbi 补新兴市场 CPI actual 兜底）。两者是互补关系，故**新增独立端点** `/macro/economic-calendar` 走 Facade，不动既有 `/macro/calendar`（akshare）避免回归。
- **融合策略（新增 `_merge` ECONOMIC_CALENDAR 分支）**：以 `country + event` 为 key 去重，`actual` / `estimate` 互补回填（任一源有 actual 即补），输出 `merged_sources` 溯源。
- **权重**：`dbnomics` / `rbi` 业务权重设为 55（高于默认 50，低于 fred 的 90），体现"新兴市场 CPI 兜底"的次级优先级。

### 改动清单
| 文件 | 改动 |
|:---|:---|
| `business/facade.py` | 新增 `_merge_calendar_events` helper；`_merge` 增加 `ECONOMIC_CALENDAR` 分支（actual 互补合并 + `calendar_merge` 指标）；`_business_weight` 表加 `dbnomics=55` / `rbi=55`；新增域方法 `get_economic_calendar` |
| `business/macro.py` | `MacroDataService` 暴露 `get_economic_calendar` 域方法 |

| `tests/test_be_arch06f_economic_calendar.py` | 7 用例：单源 / 多源 actual 回填合并 / 全源失败降级 / prefer / helper 去重 / 域方法透传 |

### 8.3 标准③破口：声明干净 ≠ 代码不依赖（P0 · 部署阻塞）

依赖链（全程无 try 保护）：

```

  └─ backend/services/futu/__init__.py:6   from .service import futu_service
       └─ backend/services/futu/service.py:16   from futu import ModifyOrderOp, TrdMarket, TrdSide
```

主镜像不含该包：`Dockerfile` 执行 `uv sync --no-dev --no-install-project`（无 `--extra datasource-*`）；`futu-api` 仅在 `datasource-us` extra，CI 只打进 `-data-subservice:us`（`.github/workflows/backend.yml:66-70`）。

实测：`python3 -c "import backend.services.futu"` → `ModuleNotFoundError: futu`。

`market_engine` 被 `bootstrap/lifecycle.py`、`routers/market.py`、`app/macro_app.py` 引用，均在 `backend.main` 链上 ⇒ **生产镜像 `uvicorn backend.main:app` 在 import 阶段崩溃**。此为 07b 修死门控时把懒加载 `_get_futu_service()` 改成 eager import 引入的回归。

修法极小：`market_engine` 仅用 `is_futu_unsupported`（在 `services/futu/utils.py`，**纯函数零 import**）+ 两处操作主服务并不持有的 OpenD 连接/本地缓存的死代码（`:313` `unsubscribe_quote`、`:332` `cache_mgr.evict_stale_cache`）。另有 6 处函数内懒加载同源风险，详见 BE-ARCH-08a。

### 8.4 标准①破口

| 缺陷 | 证据 | 后果 |
|:---|:---|:---|
| **params 键名错位** | 发送 `router.py:582-586` `{"ticker": ...}` vs 接收 `data_subservice/yfinance_worker.py:13` `params.get("symbol")`；`fetch_yfinance` 无归一（对比 Futu 有 `router.py:751-762`） | YF 的 QUOTE/HISTORY/FUND_FLOW/OPTION_CHAIN/FINANCIALS/TECH 全收到 `None`；AKShare、FMP 的 Facade 路径同病 |

### 8.5 标准②破口：长连接生产侧四处断链

消费侧与解码侧是通的（`redis_pubsub_listener` 在 API 进程启动即拉起；`quant:quotes:stream` 频道名逐字符一致；protobuf 两侧匹配），**卡在生产侧**：

| # | 断点 | 证据 |
|:---:|:---|:---|
| 1 | 推送桥接从未建立 | `data_subservice/main.py:177` `to_thread(futu_service.connect)` ⇒ `_register_push_handlers` 在工作线程 ⇒ `asyncio.get_running_loop()` 抛 `RuntimeError` ⇒ `connection_manager.py:105-106` 告警 ⇒ `set_main_loop` never called ⇒ 回调协程被丢弃（`push_handler.py:51-54`） |
| 2 | 启动零订阅 | connect 后只注册回调，无 `quote_ctx.subscribe(...)`；订阅仅为 `futu_src/quote_handler.py:81-96` 副作用。没人 subscribe ⇒ OpenD 不推 |
| 3 | 重连恢复关掉推送 | `futu_src/watchdog.py:205,308` `subscribe_push=False` |
| 4 | 子服务未接主 Redis | `docker-compose.node-s1.yml` 无 Redis 配置；`_internal/redis_client.py:20` 默认 `localhost` |
| 5 | 前端订阅不回传 | `routers/market.py:101-107` → `market_engine.py:166-172` 仅更新本地字典 |

⇒ 线上前端看到的"实时"实际是 `broadcast_loop` 每约 10s HTTP 拉快照写 Redis 再转发的轮询。

附：`routers/market.py:52` 声称的 drop-oldest 背压未实现（`market_engine.py:272-276` 直接 `await send_bytes`，失败 `pass`）；行情 WS 客户端从不发 ping，而通用 `use-ws-manager.ts:111` 发 `{type:'ping'}` 与服务端认的 `action` 字段不匹配。

### 8.6 方法论根因：为何这些缺陷长期隐形

1. **离线 stub 在构造 payload 之前短路**：`router.py:557-563` 在 `OFFLINE_MODE=1` 或 `QUANT_ENV∈{offline,testing,dev}` 时直接返回确定性 stub ⇒ 单测与 dev 环境永远走不到真实 params，8.4 的键名错位对测试完全不可见。
2. **守门测试只查静态特征**：07n 检查 import 与外部域名字面量，看不见"跨进程字段约定不一致""错误体语义不一致"。
3. **契约测试未覆盖参数层**：`SVC-01` 的 vcrpy 录制回放只回放响应，不校验请求 params 键名。

⇒ 需要一个在 `OFFLINE_MODE=0` 下真跑子服务 handler 的契约测试（BE-ARCH-08h），否则同类缺陷会持续复发。
